# Manual owner-link synthetic fixture

**Parent security review is required before any use.** This is an operator-controlled, one-fixture procedure, not a migration or an automated cleanup. Do not run it against a live project without separate authorization. Pause **all** link writers, deletes and pin changes before starting and keep them paused through confirmed cleanup or manual investigation. The advisory lock matches the save RPC, but privileged writers and pin changes need not take it. SQL table locks apply only during each statement, not between operations. Use a trusted administrator able to see all rows and lock both tables; `row_security = off` fails rather than silently applying RLS, but cannot compensate for schema drift, triggers, or an untrusted administrator.

The private fingerprint is lowercase hex SHA-256 of the UTF-8 bytes of the pinned owner's canonical PostgreSQL UUID text (`user_id::text`); it identifies an owner and is sensitive, not an authentication secret. Obtain it privately through your trusted admin process, retain the **same** fingerprint privately until confirmed cleanup, and do not put it in the journal, repo, chat, screenshots or command history. Never substitute a newly obtained fingerprint after losing the original: STOP for manual admin investigation. The generator prints SQL containing the fingerprint. Terminal scrollback, SQL Editor history, server audit/query logs, error context, clipboard and backups may record it. Check and accept your environment's retention/exposure policy before proceeding; these scripts cannot prevent such logging. Do not use credentials or tokens in SQL.

## Local synthetic ID-only reference

On a trusted local machine, create a private directory outside the repository and a file containing **only** a newly generated synthetic ID. Example, with a new dedicated directory (do not use a shared or synced location):

```sh
python3 supabase/tests/manual_fixture_generator.py init "$HOME/tubeshuffle-fixture-private"
```

The generator requires a newly created directory and exclusively creates the private file; an existing directory or reference is never reused or overwritten. If initialization fails, STOP and investigate; do not reuse the directory. Ensure the directory and file are protected by your local storage policy. This is not a real YouTube playlist ID. It is an exact-match reference, not evidence of creation. Keep only the synthetic ID there; never add project or owner identifiers, fingerprint, credentials, tokens, SQL, or results. The ID is not secret but should not be published. Remove the file and directory after confirmed cleanup according to local policy. Backups and secure deletion are platform-dependent.

## Create and cleanup

1. Privately and independently verify the authorized intended project reference and the actual project currently selected in SQL Editor from trusted project administration sources. Both must be `rkgbxjwmnlsmguhctguf`; if either is unknown, differs, or the editor destination is uncertain, STOP. From a private terminal run `python3 supabase/tests/manual_fixture_generator.py create "$HOME/tubeshuffle-fixture-private"`. Enter both references and the original fingerprint at the hidden prompts. The generator validates exact ASCII inputs before generating SQL; never edit or substitute literals yourself. Privately copy the generated **whole single DO statement** to the verified editor and execute once. Recheck the editor target immediately before execution. The statement checks exactly one matching pin, zero links for that owner and global ID absence, then inserts exactly one row with fixed timestamp `2000-01-01 00:00:00+00`. Terminal scrollback and clipboard may retain sensitive SQL; follow local policy.
2. Proceed only when the editor confirms the statement completed successfully and its transaction committed. A statement success inside an uncommitted outer transaction is not confirmation. Record only a non-sensitive confirmed-create status outside SQL history, never the fingerprint or owner ID. If an error, timeout, disconnect, ambiguous commit, pin change or any uncertainty occurs: **STOP**, keep writers paused, do not retry or delete, and require manual admin investigation.
3. Only after confirmed creation and the two-account diagnostic below, repeat the independent intended-project and current-editor verification above, even if the editor has not visibly changed. Run `python3 supabase/tests/manual_fixture_generator.py delete "$HOME/tubeshuffle-fixture-private"` and enter both independently verified references and the **original** fingerprint. Recheck the editor target immediately before executing the generated whole statement once. It requires the same pin, exactly one owner link, exactly one global ID match, and exactly one row matching owner, ID and fixed timestamp; the DELETE must affect exactly one row. Confirm its transaction committed. On any failure or ambiguity, STOP for manual admin investigation; never automatically retry or delete. A lost ID or fingerprint is an acceptable BLOCKED outcome, not permission to guess.
4. Resume writers and pin changes only after confirmed cleanup or an explicit manual admin resolution. This procedure cannot prove a historical pin was never changed and restored, that nobody recreated an identical row, or that a successful response was durably committed in every infrastructure failure; the operational pause and trusted confirmation are essential. Never treat the fixture timestamp or hash as proof of ownership by itself.

## Two-account diagnostic

Only after confirmed creation, under separately authorized testing and the same pause, run the native **Private two-account check** against the independently verified project with the pinned owner and a distinct non-owner. It reads Supabase's Data API directly, not the application's protected API; the latter denies non-owners before querying links. With the creation precondition and the operational pause, the sole owner row should be the synthetic fixture. An empty or unusable owner result is inconclusive, not a positive control. Record only the diagnostic's generic outcome; do not record account identifiers, tokens, responses, or row contents. A row returned to the non-owner is a failure. Errors or uncertain identities, targets or results require STOP and investigation. This narrowly tests visibility of one owner row through that direct read at that moment, not general RLS correctness, other operations, accounts, rows, routes or future behavior. Do not proceed to cleanup on uncertain creation or diagnostic outcomes; resolve manually first.
