# Owner links database

The initial migration was applied to the TubeShuffle project on 2026-10-29 through the Supabase Management API and recorded as version `20261029131212`. The recorded SQL was verified to match the local migration exactly. The owner pin is not yet configured; live authorization and deployment gates remain open.

Apply the migration only to an approved Supabase project using an administrative migration role capable of creating roles and assigning function ownership. It creates no owner pin. Verify a Google identity out of band, then, with protected traffic blocked, an administrator may insert exactly one verified UUID into `private.approved_owner (singleton, user_id)` and configure the same UUID as the server pin. Never expose the private schema in the Data API. Rotate by blocking traffic, changing both pins administratively, testing old and new sessions, then reopening; deleting/recreating an account requires re-verification. Do not put UUIDs or credentials in scripts or logs.

The migration uses PostgreSQL 16+ role-membership options. Run the whole migration in a single transaction: it temporarily grants the executing role SET (but not INHERIT) on the executor, and temporarily grants the executor CREATE on public, solely for function ownership transfers; both capabilities are removed afterward. A failed transaction must roll back in full; a runner that applies individual statements without a transaction can leave temporary capabilities behind. PostgreSQL can automatically grant the role creator ADMIN membership; revoking SET does **not** revoke ADMIN. The migration operator remains trusted: ADMIN can grant SET again or delegate membership, and a privileged operator may bypass the application cap and access controls. Do not give this operator or its role-administration capabilities to clients. Audit indirect membership, ADMIN, SET and INHERIT paths for anon/authenticated and any authenticator role in the deployed project, including default privileges. The local result does not establish the deployed role graph. A second application is not idempotent; rely on transactional migration history rather than re-running it.

`public.is_approved_owner()` takes no arguments and returns only a boolean. `public.save_playlist_link(id)` accepts a normalized raw ID and returns one row with `created`, `youtube_playlist_id`, `created_at`, and `limit_reached`. At the cap, the latter is true and ID/timestamp are null; an existing ID returns its original timestamp even at the cap. The application formats timestamps and handles URL normalization. Only authenticated users can invoke these functions; public and anon cannot. Links are readable/deletable only by the pinned owner; direct client INSERT/UPDATE is denied. The NOLOGIN executor has explicit RLS policies and cannot alter the pin or delete links. Administrators remain trusted and must not use alternate creators during normal operations.

Every unprivileged creator is serialized by the same transaction-scoped advisory lock; checks, count and insert are atomic and roll back together. Concurrent delete can cause a conservative cap response. Pin administration must block traffic, since a pin change is not serialized with an already-running request. Pin removal is fail-closed for subsequent operations. Authenticated JWTs may remain valid until expiry after logout.

Run `tests/owner_links.sql` against a disposable local Supabase database after applying the migration, as a privileged test operator; it rolls back fixtures. This is not a production provisioning script. SQL tests cannot establish Data API exposure, JWT verification, role inheritance in a deployed project, or concurrent execution. Before release, independently test direct Data API owner/non-owner/anon/forged/expired JWTs, private schema exposure, and parallel saves at 4,999 (same and distinct IDs), delete races, rollback/retry, and pagination beyond 1,000. Parent security review and live proof remain required.
