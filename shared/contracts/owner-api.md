# Proposed owner API v1 — not implemented

Only link CRUD below uses these rules; existing YouTube proxies have their own request limits, query semantics and operational errors (`{ "error": string }`). If future owner protection is added to those proxies, guard failures use the structured auth errors below, but successful responses and legacy operational errors remain unchanged. This is a proposal, not a statement about current handlers.

## Authentication and precedence

Paths are relative to the deployment origin. Match a route and method first: an unsupported method returns 405 with `Allow` (`GET, POST` or `DELETE`), independent of credentials. For a supported method validate credentials before query, body, media type, path ID, CSRF, storage or YouTube work. Accept a provider-verified bearer access token or same-origin session cookie; never trust unverified claims. An Authorization header must be exactly a single Bearer credential with a nonempty token (scheme case-insensitive); malformed, invalid, expired or revoked credentials return 401 `unauthenticated` and never fall back to a cookie. Missing credentials also return 401. A provider outage or indeterminate verification returns 503 `auth_unavailable`, not 401. Verified non-owner returns 403 `forbidden`; owner is a server-pinned identity, not request data. Never disclose owner identity. Cookie-authenticated POST/DELETE require same-origin Origin and CSRF verification; failure is 403 `forbidden` after auth and before request validation. No failed auth or link CRUD calls YouTube.

For authenticated authorized requests, check in order: CSRF (if applicable), query/path syntax, body byte length, media type, JSON syntax/schema/value. CRUD accepts no query parameters, including an empty `?`. GET and DELETE require zero body bytes; nonempty bodies up to 4096 bytes return 400 `invalid_request` regardless of media type. POST checks the actual body bytes before decoding; >4096 bytes returns 413 `payload_too_large`. POST requires `application/json` (case-insensitive media type, optional parameters; charset if supplied must be UTF-8), otherwise 415 `unsupported_media_type`, including for an empty body; malformed UTF-8, malformed JSON, duplicate keys, non-object JSON, unknown/missing fields and invalid values return 400 `invalid_request`. Path IDs are percent-decoded exactly once, malformed escapes/UTF-8 and extra segments rejected; DELETE accepts only a raw ID after decoding, not a URL. Request and response JSON is UTF-8. Rate limiting may reject authenticated requests at any point after auth with 429 `rate_limited`; when known, `Retry-After` is a nonnegative integer number of seconds until retry, rounded up. Storage failure returns 500 `internal_error`. All responses including errors have `Cache-Control: no-store`.

Errors are JSON `{ "error": { "code": string, "message": string } }`; code is stable, message is human-readable and not a parsing key. Never include secrets or token values. 204 has zero response bytes (fixture `null` represents absence). These rules do not change existing proxy limits or operational error envelopes.

## Links and normalization

JSON link DTO has exactly two required non-null string fields: `youtubePlaylistId` and `createdAt`. ID matches ASCII `^[A-Za-z0-9_-]{10,80}$`, is case-sensitive and is never case-folded. `createdAt` is a valid Gregorian UTC RFC 3339 instant formatted `YYYY-MM-DDTHH:mm:ss.sssZ`, derived from the database instant rounded down to milliseconds; four-digit years 0001–9999. Owner ID, title, metadata, playlist contents and history are not uploaded.

POST body is exactly `{ "playlistId": string }`. Trim ASCII space, tab, CR and LF from its ends. If it matches the ID grammar, use it unchanged. Otherwise parse as an absolute HTTPS URL without userinfo or non-default port, host case-insensitively exactly `youtube.com`, `www.youtube.com` or `m.youtube.com`, path exactly `/playlist` or `/watch`. Require exactly one `list` query parameter; URL-decode it once using standard query decoding, then apply the same ID grammar. Other query parameters and fragments are ignored. Reject other hosts, paths, schemes, malformed URLs, repeated or missing `list`, and decoded invalid IDs. Never fetch the URL or validate playlist existence with YouTube. Normalization is server-side before lookup, uniqueness and cap checks, so URL and ID forms identify the same link.

* `GET /api/playlist-links`: 200 `{ "links": [link, ...] }`; zero to 5000 links, no pagination. Sort ascending by `createdAt`, then ID using ASCII byte order (not locale collation).
* `POST /api/playlist-links`: 201 `{ "link": link }` for a new normalized ID; 200 same DTO with original `createdAt` for an existing ID, even at the cap. A new distinct ID at 5000 returns 409 `link_limit`.
* `DELETE /api/playlist-links/[playlistId]`: 204 with no body for a valid ID whether present or absent. Only the current owner's row can be removed.

Enforce unique `(owner, youtubePlaylistId)` and cap with one serializable per-owner transaction or equivalent per-owner lock shared by all creators: check existing first, then count and insert atomically. Concurrent same-ID requests produce one 201 and remaining 200 with the same original DTO; concurrent distinct IDs competing for the final slot produce one 201 and the rest 409. A failed transaction must not partially create a link. A retry after an unknown outcome is safe and returns 200 if the insertion committed. Constraints must also protect any permitted direct database writes, not just the route.

Cloud unlink removes only the owner's bookmark, not local playlists or history; local delete is separate and currently may leave orphan history. Sign-out removes access, not local data.
