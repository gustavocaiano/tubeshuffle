# Proposed transfer v1 — not implemented

## Wire format and validation

A file is one UTF-8 JSON object without BOM, at most 10,485,760 encoded bytes, measured before decoding. Bound input buffers and decoded allocations; reject over-limit input before parsing and check array sizes before allocating records or writing. The exact top-level keys are `format`, `version`, `exportedAt`, `playlists`, `videos`, `history`; format is `tubeshuffle-transfer`, version is numeric integer 1. Unknown fields at every level and duplicate object keys after JSON escape decoding (including escaped equivalents) are errors. Reject malformed UTF-8, unpaired surrogates, non-JSON/nonfinite numbers. Strings count Unicode scalar values, equality is exact scalar sequence, case-sensitive, without normalization or locale folding. Text permits controls; IDs prohibit U+0000–U+001F and U+007F–U+009F. IDs are opaque 1–200 scalars, never parse composite IDs. YouTube playlist IDs match ASCII `^[A-Za-z0-9_-]{10,80}$`; video IDs match `^[A-Za-z0-9_-]{1,80}$`.

Timestamps are strings `YYYY-MM-DDTHH:mm:ss.sssZ`, Gregorian real dates years 0001–9999, 00–23 hours, 00–59 minutes and seconds (no leap seconds), valid leap days. Integers are mathematical integers, including exponent notation, between 0 and 9007199254740991 inclusive unless a smaller bound is stated; reject numbers not exactly representable as IEEE-754 binary64 (including when parsing would round). Decimal seconds are finite binary64 numbers from 0 through 864000; compare numeric values, not lexemes. Optional means absent or the stated type, never null. Required nullable fields must be present and may be null. JSON object key order is irrelevant; arrays preserve order.

* `playlists`: array <= 5000. Required `id` (ID), `youtubeId` (playlist ID), `title` (string <=1000), `description`, `thumbnail`, `channelTitle` (each null or string <=10000), `videoCount` (integer <=1000000), `createdAt`, `updatedAt` (timestamps). IDs and youtubeIds unique independently.
* `videos`: array <=50000. Required `id`, `playlistId` (IDs), `youtubeId` (video ID), `title`, `channelTitle`, `thumbnail` (strings <=10000), `duration` (seconds), `position` (safe integer). Optional `viewCount`, `likeCount` (safe integers), `description`, `categoryId` (strings <=10000), `tags` (array <=100 strings each <=200), `publishedAt` (timestamp). IDs globally unique within videos, `(playlistId, position)` unique, playlistId must name a source playlist. Repeated youtubeId is allowed with distinct stable IDs and positions. An ID may occur in different record-type namespaces.
* `history`: array <=100000. Required `id`, `playlistId`, `videoId` (IDs), `watchedAt` (timestamp), `watchedSeconds` (seconds), `completed` (boolean); event IDs unique. A missing playlist, missing video, or video belonging to a different source playlist is an orphan, omitted and reported, not a fatal reference error. Test source references before looking at destination. No destination ID can make an orphan valid.

Failure precedence: bytes/UTF-8/JSON including duplicate keys; envelope/unknown version; field/schema/count/uniqueness; video references; destination invariants/collisions; preview staleness/transaction; storage. Report only the first category in this order. Sort its diagnostics by kind, then ID, then reason in Unicode scalar order and return at most the first 100, including repeated identical diagnostics. Return `omittedDiagnostics`, the number omitted (zero when complete); counting saturates at 9007199254740991 total diagnostics, so at saturation the omitted count is a lower bound, not an exact count. For unknown field names exceeding 200 scalars or containing unpaired surrogates, substitute `<redacted>`; each unknown field still contributes one diagnostic, even when several render identically. Invalid IDs are represented by an empty diagnostic ID; never retain invalid values in identity indexes. Check each uniqueness key independently when its constituent fields are valid, even if the record has unrelated errors. Count-limit diagnostics represent the limit violation once per array; records beyond the limit are not inspected or counted as diagnostics. Do not report success counts or a partial file for rejected operations. Future versions return `unsupported_version`, never attempt migration. Array maxima and byte maximum apply independently, not a promise all maxima fit simultaneously.

## Export and legacy compatibility

Take one consistent storage snapshot; never include credentials, media, queue, transient UI state or suggestions. Export only records actually retained in storage. Browser composite video IDs may have overwritten earlier occurrences: never invent them; warn `occurrences_unrecoverable` when known and state this limitation even when detection is impossible. Resolve history against the source snapshot, omit and report each orphan with reason `missing_playlist`, then `missing_video`, then `cross_playlist` (first applicable). Portable import also accepts and omits such legacy files, but new exports do not contain orphans.

Preserve valid legacy values and absent optional fields; required nulls remain null, never conflate absent and null. Legacy timestamp strings must denote a valid Gregorian RFC 3339 instant with explicit `Z` or numeric offset, no leap second, and at most three fractional digits (or additional digits all zero). Convert losslessly to UTC with exactly three fractional digits; reject out-of-range years or nonzero sub-millisecond precision as `unrepresentable_timestamp`, never round. Verify legacy numeric values against exact bounds above (including common counts above 1 billion), and validate all other values as wire fields. Invalid/unrepresentable values, duplicate YouTube playlist IDs or positions, and limits produce a diagnostic naming the offending records/limit and no file; do not silently truncate, merge, delete, or repair. Present recovery as user-directed cleanup/export of a smaller selection, retaining the original library. If complete encoded output exceeds the byte limit, report `file_too_large` and required bytes, not a partial file.

Before validation, construct a new wire candidate from the IndexedDB snapshot: for the six optional video properties only, an absent property or an own property whose value is JavaScript `undefined` becomes absent. Copy every other value unchanged, including null, malformed values and unknown keys, for validation; never rely on JSON.stringify dropping values, and never mutate the snapshot. Undefined in required or unknown fields is an error. Validate before serialization, including nested arrays; undefined elements, null or wrong types are errors. A valid defined optional value must survive exactly (except the specified timestamp normalization). Swift must encode absent optional values by omitting keys, not encoding null; its decoder must distinguish an absent key from explicit null and reject the latter. This mapping is specific to stored JS undefined; JSON itself cannot represent it.

## Preview and transactional merge

Validate source completely, then read destination as a consistent snapshot. Destination must satisfy the same record constraints and unique playlist youtubeIds; if not, abort with diagnostics and user-directed cleanup, never arbitrarily choose one. Preview includes snapshot revision and a deterministic list of operations/reports. The user explicitly commits the preview. In one actual persistence transaction, re-read/recheck destination invariants, revision, identities, references and all collisions before any writes. If changed since preview, abort `stale_preview` and require a fresh preview. Commit all planned creates together; any write/commit failure rolls back everything and returns `storage_failure`. No partial success after a fatal error. External changes before that transaction remain intact; rollback concerns only import writes.

Match playlists by youtubeId, preserving the destination stable ID. If source playlist ID is already used by a different destination playlist, even if youtubeId matches another, abort `playlist_id_collision`; otherwise a missing playlist retains source ID. Compare matched playlist fields after substituting destination ID; createdAt and all metadata participate. Identical records count identical; differing fields remain unchanged and report `playlist/fields`. A differing playlist does not prevent safe child reconciliation. Never choose timestamp winners or delete.

Process videos in source array order after reserving proven or explicitly confirmed pairs. An existing source ID in another destination playlist or with a different YouTube ID is `video/identity`, unmapped. Equal opaque IDs, mapped playlist and YouTube ID are necessary for an equal-ID match but **not sufficient**: a legacy composite ID can be regenerated after removal and re-addition. Never infer provenance by parsing ID text, equality, timestamps, metadata, position, event equality, previous transfer, or presumed lineage. V1 carries no trusted occurrence provenance by default, including for IDs created by older browser versions or copied across devices. A safe refresh introduced later cannot retroactively prove continuity. Without independent trustworthy continuity evidence or an explicit evidence-backed user confirmation, report `video/ambiguous_occurrence`, leave the video unmapped, and retain both libraries and the source backup. An occupied equal ID must not be created, overwritten, renamed to evade the conflict, or matched by any fallback.

Automatic mapping for any equal or independent IDs requires independently verified stable upstream playlist-item identity, equal and unique within the matched playlist, or equivalent trustworthy continuity evidence establishing this particular occurrence survived without removal/re-addition across both lineages. Evidence must be explicit, validated, and bound to the relevant source and destination snapshots; no such evidence is provided by the V1 wire format. A future provenance mechanism requires a separately specified trusted migration boundary, including preservation across all mutations; it cannot retroactively certify legacy records. When evidence is unavailable, a preview may offer an explicit user-confirmed one-to-one mapping, including equal-ID pairs: show source and destination playlist, occurrence IDs, positions, YouTube IDs, and relevant history; require equal YouTube IDs, distinct targets, explicit confirmation per pair and revision-bound revalidation. Explain that users must establish the same occurrence from external evidence; position or appearance alone is insufficient and mistaken confirmation risks misattachment. A user can decline/cancel without writes. Confirmation is an assertion, not proof inferred by the implementation. Reserve all proven matches and accepted pairs before processing creates; compare fields after substituting mapped IDs, retaining destination IDs. Reject duplicate targets, invalid pairs, changed snapshots or identity collisions; never override a proven match.

An unused source ID without an accepted mapping is created only if its position is free and no unreserved pre-existing destination occurrence with that YouTube ID exists in the mapped playlist; otherwise report `video/position` for occupied positions or `video/ambiguous_occurrence` for potentially moved/repeated items, leaving it unmapped. Include planned creates in position checks; distinct source occurrences can be created together into an empty playlist. Never attach history for an unmapped occurrence by event ID or any other fallback. A repeated import is a no-write operation only when mappings are again proven or explicitly confirmed; absent such evidence it remains a reported conflict, not an identical match. A persisted user assertion may be reused only if explicitly authorized and bound to the exact source, destination occurrence and unchanged relevant lineage/revision, with revalidation; otherwise require fresh confirmation. Existing event IDs provide idempotence only after a safe occurrence mapping. On conflict retain both original libraries and source file; offer backup/export, inspection of external playlist-item evidence and retry with a confirmed pair, or import into a separate empty library/profile. Never promise evidence is available or destroy data to resolve ambiguity.

For each non-orphan source event, require its source video to have a safe mapped occurrence above. If unmapped, report `history/unmapped_video`, do not create it even if an opaque ID happens to exist. Substitute both mapped IDs, then compare event by stable ID: absent creates; identical counts identical; differing fields report `history/fields`, leave unchanged. Destination video must belong to mapped playlist; otherwise abort invariant failure. Never attach across playlists. Event/playlist/video IDs occupy separate namespaces. Repeat imports with proven or confirmed occurrence mappings are no-ops; reports distinguish created, identical, conflicts and omitted orphans for each kind. Reports use `{created:{playlists,videos,history}, identical:{playlists,videos,history}, conflicts:[{kind,id,reason}], omittedOrphans:[{id,reason}]}`, conflicts ordered playlist, video, history then source array order; orphans in source history order. Counts reflect records processed, not attempted writes. Conflicts do not count as identical or created.

`../fixtures/transfer-v1.json` contains a historical source snapshot at its top level (including an orphan) plus a fixture-only `vectors` key; remove `vectors` before treating the example as wire input. Its language-neutral merge vectors provide full source, destination, and expected outcome; fixture-only `confirmedPairs` are explicit user assertions based on external evidence, not wire provenance. Validation and legacy vectors specify raw bytes or generators when JSON objects cannot represent the test. They are specifications, not evidence of an importer. Both browser and Swift implementations must consume all vectors, including `equalLegacyOccurrences` and refresh routes, and add real persistence fault/concurrency tests. The old orphan example must not be interpreted as an export result.

## Mandatory refresh/sync integration gate

Before enabling any route that can destructively refresh a library supporting transfer—including syncPlaylist, importing/re-importing an already existing YouTube playlist, and any shared upsert or alternate entry point— implement a single atomic transaction over playlist, occurrence and history changes: preserve each proven surviving occurrence ID, or bijectively remap it and every referencing history ID to a verified same occurrence. Never collapse repeated occurrences or reassign history from removed/ambiguous items. Preserve removed/ambiguous occurrences and their history in a valid recoverable representation, or abort without writes; no orphaning, silent deletion or lossy export. Recheck revision and all IDs/references/collisions inside the transaction; failures and stale previews roll back all refresh writes. Subsequent watched filtering and export must resolve every retained event to the same occurrence. If these guarantees cannot be met, block refresh before destructive work with a clear explanation; allow backup export, retain the library and retry after safe sync support is installed. This gate applies regardless of whether an import happened. Current browser sync deletes and regenerates composite IDs and does not implement this requirement; transfer support must not ship while that unsafe path remains available. Fixture scenarios are obligations, not proof of implementation.
